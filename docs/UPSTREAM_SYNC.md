# 업스트림 변경과 공개판 유지

이 공개판은 운영에 사용되는 앱 코드에서 공개 가능한 변경을 가져오되, 독립된 Git 이력과 설치자용 기본값을 유지합니다. 각 설치자의 DB, 로그인 계정, 외부 연동, 저장된 거래와 계획은 저장소 동기화 대상이 아닙니다. 코드를 업데이트해도 설치자의 DB 마이그레이션과 앱 배포가 자동 완료되지는 않습니다.

이 문서는 동기화 설계와 유지 기준을 설명합니다. 인증 설정과 최초 실행은 별도 확인이 필요하며, 문서나 테스트만으로 자동 발행이 활성화되었다고 보장하지 않습니다. 현재 공개 코드와 CI 실행 결과는 이 저장소에서 확인합니다.

## 변경을 가져오는 방식

1. 신뢰된 업스트림 브랜치의 동일 commit이 원본 테스트와 build를 통과합니다.
2. 마지막 성공 기준, 현재 공개판, 새 업스트림 변경을 3방향으로 비교합니다. 공개판에서 별도로 수정한 부분을 유지하며 공통 기능 변경을 합칩니다.
3. 명시적인 파일 허용 목록과 비공개 값 검사를 통과한 파일만 독립 archive로 묶습니다. 원본 Git 이력, 로컬 환경 파일, 인증정보, 도구 상태와 금융자료를 넣지 않습니다. 사용한 정책의 실제 내용 hash를 후보 digest에 결합합니다.
4. 별도 job이 발행용 인증정보 없이 archive에서 `npm ci`, `npm run doctor`, `npm test`, `npm run build`를 실행합니다.
5. 분리된 발행 job이 검증한 파일과 후보 digest·정책 hash를 다시 확인한 뒤 현재 공개 `main` 위에 새 commit으로 반영합니다. 정책의 버전 번호만으로 검증 결과를 재사용하지 않습니다. 강제 push하지 않으며, 중간에 공개판이 바뀌었다면 다시 병합·검증합니다.
6. 공개 반영 성공 후에만 다음 동기화를 위한 비공개 기준을 갱신하고 해당 후보·정책 hash를 함께 기록합니다. 공개 반영과 상태 기록 중 하나만 성공하면 부분 완료로 처리합니다.

새 경로, 수동검토 대상으로 지정한 보호 파일 변경, 확인되지 않은 삭제와 병합 충돌은 자동 반영을 중단합니다. 동기화에서 제외한 문서·설정은 공개판의 현재 파일을 유지합니다. 모호한 변경을 추측하거나 검사를 생략하여 공개하지 않습니다. 업스트림 검증과 별도로 실제 공개 후보 전체를 검증하므로 공개판의 독립 변경도 같은 테스트 대상이 됩니다.

새 기능에 신규 파일이 필요하면 유지관리자가 공개 적합성을 검토하고, 같은 기능 변경에서 **개별 파일의 정확한 경로**를 비공개 승인 목록에 등록합니다. 승인되지 않은 경로가 자동으로 공개되거나 폴더 전체가 포괄 승인되지는 않습니다. 신규 경로 승인도 민감 값·보호 경로 검사를 대신하지 않습니다.

## 공개판에서 의도적으로 유지하는 부분

공개 설치를 위해 만든 문서·라이선스·환경 예시, 빈 설치 정책과 최초 관리자 bootstrap은 원본 운영 설정과 구분해 보호합니다. 문서처럼 동기화에서 제외한 경로는 공개판의 현재 내용을 유지하며, 수동검토 대상으로 지정한 설치 설정 등이 업스트림에서 바뀌면 자동 반영을 중단하고 사람이 검토합니다.

- `lib/finance/installation-policy.ts`의 업종 연결·추정 제외·시트 별칭·과거완료 기준은 설치자가 선택하는 정책입니다. 다른 조직의 사업자명이나 개인별 규칙으로 바꾸지 않습니다.
- `supabase/operations/bootstrap_workspace.sql`의 신뢰된 최초 관리자 지정 절차를 유지합니다. 최초 방문자에게 권한을 주거나 다른 설치의 사용자 ID를 복사하지 않습니다.
- 공개 README·설치/개발 문서, 보안 안내와 서드파티 고지를 유지합니다. 다른 설치의 운영 접속 기록과 환경값을 넣지 않습니다.
- 설치자용 환경 파일에는 비어 있는 값이나 합성 예시만 둡니다. 기존 설치의 키·DB 주소·계좌 연결이 제공되는 것처럼 만들지 않습니다.

정확한 자동 반영 범위는 유지관리자가 검토한 정책을 따릅니다. 보호된 파일을 보존한다는 이유로 필요한 보안 수정이나 설치 절차 변경을 영구히 배제하지는 않습니다. 자동화가 멈추면 공개용 수정과 검증을 명시적으로 진행합니다.

## 보안과 공개 검사의 한계

경로 제한, 비공개 값 검사와 합성 테스트는 공개 범위를 지키기 위한 장치입니다. **테스트가 통과해도 모든 개인정보나 재무자료가 제거되었다는 보장은 없습니다.** 새 비공개 식별자·값·자료 형식이 생기면 유지관리자는 비공개 검사 정책과 합성 검증을 먼저 갱신해야 합니다. 실제 값을 공개 issue·fixture·문서에 붙이지 않습니다.

발행 인증에는 대상 저장소 하나로 제한된 GitHub App의 단기 설치 토큰을 권장합니다. App의 private key와 토큰은 Git에 저장하지 않으며 공개판 테스트 job에 전달하지 않습니다. 일반 코드 쓰기는 Contents 권한을 사용하고 workflow 파일까지 바꿀 때만 추가 Workflows 권한을 검토합니다. [GitHub 공식 App 인증 안내](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/making-authenticated-api-requests-with-a-github-app-in-a-github-actions-workflow), [파일 변경 권한](https://docs.github.com/en/rest/repos/contents#create-or-update-file-contents)

인증 토큰으로 실행되는 push와 공개 CI 실행 여부는 서로 확인해야 합니다. GitHub의 기본 `GITHUB_TOKEN`으로 만든 push는 후속 push workflow를 실행하지 않으며, 별도 App 설치 토큰을 사용하는 방식은 후속 이벤트를 만들 수 있습니다. [GitHub 공식 트리거 규칙](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow)

## 기여자와 설치자가 할 일

공개판에서 수정할 때는 기존 거래 원본·수동 분류·저장 계획·계속 제외, RLS와 권한·서명·충돌 검사를 유지합니다. 공개판에 독립적인 개선을 제안할 수 있으며 자동 동기화는 이 변경을 통째로 덮어쓰는 허가가 아닙니다. 충돌은 유지관리자가 양쪽 의도를 검토한 뒤 해결합니다.

업데이트 전 자신의 변경과 DB 적용 이력을 확인하고 [개발 가이드](DEVELOPMENT.md)를 따릅니다. 새 설치나 관리자 추가는 각자의 인증과 bootstrap·초대 절차를 사용합니다. 원본 테스트 통과, 공개 후보 검증, 공개 Git 반영, 공개 CI와 자신의 배포·실제 연동 확인은 각각 다른 상태입니다.

기여 기준은 [CONTRIBUTING.md](../CONTRIBUTING.md), 금융 계산 계약은 [OPERATING_RULES.md](OPERATING_RULES.md), 민감한 보안 제보는 [SECURITY.md](../SECURITY.md)를 참고하세요.
