# 멀린 자금관리 운영·개발 기준

공개 설치에서 유지할 거래 보존·금융 계산·화면·개발 계약을 설명한다. 설치별 사업자·개인 분류 규칙과 실제 재무자료는 포함하지 않는다.

**목표는 실제 통장을 근거로 어느 사업자의 어느 계좌에 언제까지 얼마가 필요한지 바로 판단할 수 있게 하는 것이다.**

## 이 문서를 사용하는 방법

- **GOV-01 — 최신 명시 지시 우선:** 새 사용자 지시가 기존 기준을 변경하면 변경 범위와 적용 시점을 확인하고 이 문서도 같은 작업에서 갱신한다. 과거 대화의 일회성 요청을 새 거래 전체에 확대하지 않는다.
- **GOV-02 — 기준과 저장 상태 구분:** 이 문서는 운영 기준이다. 모든 규칙이 DB에 저장되었거나 모든 기능이 구현됐다는 증거가 아니다. 현재 소스·테스트·공동 설정·원본 근거로 실제 동작을 확인한다.
- **GOV-03 — 변경 범위 보존:** 이 문서의 과목표나 예외 목록을 읽는 것만으로 운영 거래의 일괄 수정·삭제가 허가되지는 않는다. 사용자 요청의 사업자·기간·입출금·대상 거래 범위 안에서 변경한다.
- **GOV-04 — 계정에 독립적인 인수인계:** 이전 ChatGPT 대화, 특정 PC 경로, 브라우저 세션 또는 Sites 작업공간 없이 저장소의 문서·소스·테스트로 개발을 이어갈 수 있어야 한다. 규칙 ID는 유지하며 폐기된 규칙도 대체 규칙과 이유를 남긴다.

새 담당자는 [AGENTS.md](../AGENTS.md), 이 문서, [README](../README.md), [설치·개발 가이드](DEVELOPMENT.md)를 읽고 현재 브랜치·미커밋 변경·DB 적용 기록을 확인한다. 구현과 기준이 다르면 먼저 차이를 기록하고 요청 범위에 맞게 해결한다.

## 1. 거래 원본과 동기화

| ID | 기준 |
| --- | --- |
| DATA-01 | 거래일·입출금·금액·잔액의 근거는 실제 통장 내역이다. 추정한 거래나 상대방을 실제 거래처럼 생성하지 않는다. 원본에 없는 출금을 만들지 않는다. |
| DATA-02 | Google 시트와 Clobe는 자료를 가져오는 경로다. 은행 원본 수집 시각, 대시보드 저장 시각, 버튼을 누른 시각을 구분한다. 오래된 수집 잔액을 실시간 은행 잔액으로 표시하지 않는다. |
| DATA-03 | 일반적인 최신 동기화는 신규 거래만 추가한다. 기존 거래의 날짜·금액·적요·원본·메모·수동 과목을 덮어쓰거나 삭제하지 않는다. 원본 재구성처럼 별도로 요청한 작업은 일반 동기화와 구분한다. |
| DATA-04 | 날짜가 같다는 이유로 중복을 제거하지 않는다. 동일 계좌의 날짜·입출금·금액·명시 내역·잔액·거래시간·원본 식별자를 함께 대조한다. 근거가 부족하거나 복수 후보가 있으면 보류한다. |
| DATA-05 | 실제로 같은 거래면 다시 저장하지 않고 중복으로 처리한다. 확인된 동일 거래가 계속 보류 목록에 나타나지 않아야 한다. 같은 날짜·금액이라도 별도 이동이면 두 건을 유지한다. |
| DATA-06 | 사용자가 대시보드에서 지정한 계정과목과 수동 분류를 보존한다. 새 거래는 저장된 사용자 규칙과 확인된 연결을 사용하며, 근거가 없는 과목은 미분류로 남긴다. 시트의 과목 문자열만으로 기존 과목을 교체하지 않는다. |
| DATA-07 | Clobe 최신 동기화는 저장된 통장 연결 전체의 최근 2개월, 즉 지난달 1일부터 한국시간 오늘까지를 월별 대조한다. 신규 거래가 없어도 현재 수집 잔액과 계획용 은행 출금 근거를 갱신한다. 은행 재수집을 실행한 것으로 표시하지 않는다. |
| DATA-08 | Google 시트 최신 동기화는 등록한 모든 통장 시트의 전체 기간을 대조하되 신규 거래만 저장한다. Clobe의 최근 2개월 제한을 시트의 기존 거래 대조 범위에 잘못 적용하지 않는다. |
| DATA-09 | 저장 후 거래내역·미분류 정리·자금현황·통합분석·가용자금 계획은 같은 공동 자료를 읽는다. 숨겨진 탭은 변경 신호를 모았다가 표시될 때 갱신하고, 저장보다 오래된 조회로 최신 상태를 덮어쓰지 않는다. |
| DATA-10 | 저장 성공과 화면 재조회 성공, 일부 반영과 전체 완료를 구분한다. 실패한 범위를 완료로 표시하거나 조회 실패를 0원·거래 없음으로 처리하지 않는다. 불명확한 쓰기를 복구할 때도 같은 거래가 추가되지 않게 한다. |
| DATA-11 | 원본 표시를 개선할 때 원본 문구는 보존한다. 공백 정규화 등 비교용 처리가 금융정보 변경을 허용하는 근거가 되어서는 안 된다. 원본 ID·날짜·금액·잔액의 실제 충돌은 별도로 검토한다. |

세부 연결·보류·중복 기준은 [시트 동기화](SHEET_SYNC.md), [Clobe 연결](CLOBE.md), [개발 가이드](DEVELOPMENT.md)을 함께 따른다.

## 2. 현재 잔액과 필요자금

| ID | 기준 |
| --- | --- |
| CASH-01 | 사업자별로 계산하고, 여러 통장은 계좌별 잔액과 부족액까지 나눈다. 다른 사업자 또는 다른 통장의 여유자금으로 특정 계좌 부족액을 임의 상쇄하지 않는다. |
| CASH-02 | 계산 기준은 현재 기록 잔액이다. 혼동을 주는 별도 ‘계획 기준 잔액’을 다시 도입하지 않는다. 계좌별 짧은 통장명·잔액과 원본 수집 시각을 함께 표시한다. |
| CASH-03 | 지출 후 잔액은 현재 기록 잔액에서 남은 지출을 차감한다. 이미 현재 잔액에 반영된 출금을 남은 지출로 다시 차감하지 않는다. 유보액이 있으면 차감 전후를 구분한다. |
| CASH-04 | 필요한 자금은 사업자 → 출금 계좌 → 필요한 날짜 → 추가 부족액 → 사유 순서로 설명할 수 있어야 한다. 해당일까지의 누적 지급 일정과 확인된 자금 유입을 사용하며, 일별 부족액을 단순 합산해 같은 부족액을 중복 요구하지 않는다. |
| CASH-05 | 실제 입금되었거나 이미 보충한 자금은 최신 잔액과 연결해 다시 계산한다. 완료 지출·입금·보충액을 이후 필요자금에 중복 반영하지 않는다. 날짜 경과만으로 미지급 의무를 완료 처리하지 않는다. |
| CASH-06 | 현금 투영의 정산 예정액은 아직 입금되지 않은 미래 지급일·순지급액만 포함한다. 통장 입금이 확인된 금액은 다시 더하지 않는다. 오늘 또는 지난 지급일의 미확인 정산을 현금처럼 확정하지 않는다. 이 가산 조건을 달력 표시의 필터로 재사용하지 않는다. |
| CASH-07 | 계좌·날짜·잔액이 불명확하면 그 범위를 표시하고 임의로 배정하지 않는다. 한 통장이라도 잔액이 불명확하면 사업자 합계를 확정하는 대신 확인된 소계를 구분한다. |

실제 정산의 계산과 연결은 [Toss 정산 연동](TOSS.md)을 따른다. 지급일은 API에서 확인한 날짜를 사용하며 상점별 지급 주기를 임의로 추정하지 않는다.

## 3. 지출계획·고정비·카드·세금

| ID | 기준 |
| --- | --- |
| PLAN-01 | 사용자가 고른 계획 시작일·종료일을 유지한다. 날짜가 지나거나 동기화·메뉴 이동을 했다는 이유로 시작일을 자동으로 밀지 않는다. 날짜 선택으로 양 끝을 포함해 조회한다. |
| PLAN-02 | 선택 기간의 지난 날짜와 예산이 소진된 항목도 계획표에 유지한다. 예상액과 실제 출금이 같으면 한 번만 표시하고, 다르면 예상액에 적색 취소선을 긋고 실제액을 표시한다. |
| PLAN-03 | 은행 조회 범위 완료와 개별 계획의 출금 연결은 다른 상태다. 잔액이 바뀌었다는 사실만으로 모든 계획을 지급 완료로 표시하지 않는다. 동일 사업자·계좌·날짜·금액·명시 내역 등 근거로 연결하며 같은 출금을 한 번만 반영한다. |
| PLAN-04 | 자동 연결이 불명확한 항목은 사용자가 실제 출금일·누적 출금액·메모·완료 여부를 확인하고 수정할 수 있어야 한다. 수동 확인은 계획의 근거이며 실제 통장 거래·잔액·과목을 생성하거나 바꾸지 않는다. |
| PLAN-05 | 미래 결제일·청구액의 계획 수정과 실제 출금 완료 확인을 구분한다. 계획은 미래 날짜로 편집할 수 있어야 하며, 미래 예정 지출을 이미 출금한 사실로 저장하지 않는다. |
| PLAN-06 | 사용자가 수정한 금액·날짜·계좌·메모·제외 상태를 동기화와 자동 추정이 덮어쓰지 않는다. 다른 관리자의 변경과 충돌하거나 저장에 실패하면 입력값을 보존하고 최신 상태를 확인하게 한다. |
| PLAN-07 | 고정비는 합계만 표시하지 않고 품목별 금액·지급일·출금계좌를 확인·수정·추가·제외할 수 있어야 한다. 모든 사업자의 계획과 월별 필요자금에 같은 설정을 사용한다. |
| PLAN-08 | 고정비 수정·추가·제외는 ‘이번 달만 / 이번 달부터 계속’을 선택한다. 이전 월과 별도 월 예외를 보존하고, 계속 제외한 항목이 다음 달이나 동기화 후 다시 생기지 않게 한다. |
| PLAN-09 | 카드 결제대금은 결제일과 청구액이 있는 지출계획으로 관리한다. 사용처별 카드 승인 합계를 확정 청구액으로 간주하지 않는다. 같은 청구가 기존 카드계획·구독료·세금 할부에 포함됐는지 확인하고 중복 계산하지 않는다. |
| PLAN-10 | 할부는 시작월·종료월·회차와 월별 금액을 관리한다. 종료월 다음 달부터 계획에서 빠지며, 회차가 끝났다는 이유만으로 실제 납부 완료를 추정하지 않는다. 원금·확인된 수수료·이자는 근거에 맞게 구분한다. |
| PLAN-11 | 세금은 금액·납부기한·납부받는 계좌·납부 상태를 기록한다. 일회성 미납 일정으로 등록하고 사업자별 계획·필요자금·달력에 연결한다. 출금할 회사 통장과 수취용 가상계좌를 혼동하지 않는다. |
| PLAN-12 | 미납 세금은 가용자금 계획 상단에 적색 알림을 유지한다. 조회 기간 밖이거나 계획에서 제외되거나 기한이 지났어도 납부 완료로 확인하기 전에는 알림을 없애지 않는다. 완료 상태 기록은 실제 이체 실행과 구분한다. |
| PLAN-13 | 지출 달력과 계획표를 검산할 때 같은 기간·사업자·계좌 범위에서 달력의 ‘예정’ 합계와 날짜 미정·지난 예정일의 미지급 예산을 구분해 계획표의 ‘남은 지출 합계’와 대조한다. 달력의 실제 출금·수동 확인 합계를 남은 지출에 다시 더하지 않는다. 표의 원예산·실제 출금 표시를 잔여액으로 잘못 합산하지 않는다. 계좌 미지정 금액은 날짜별 합계에 이미 포함됐는지 확인하고 다시 더하지 않는다. 차이가 있으면 제외 범위나 계산 원인을 확인하며 일치로 단정하지 않는다. |
| PLAN-14 | 동기화 후 검증된 통장 출금으로 계획이 연결되면 실제 원본 날짜·계좌·금액으로 표시한다. 계획표에서도 연결된 실제 지급일을 확인할 수 있어야 하며 여러 지급일은 날짜별로 구분한다. 일부 출금은 실제액과 남은 예정액을 나누고, 남은 예산이 0이거나 명시적으로 지급 완료가 확인되면 예정 줄을 없앤다. 예산보다 적게 한 번 출금됐다는 사실만으로 완납을 추정하지 않는다. 수동 누적 확인과 세금 납부 완료 상태만으로 존재하지 않는 은행 거래를 만들지 않는다. 과거 패턴으로 정한 미래 날짜는 예정일이며, 지급일이 불규칙한 남은 월예산을 한 날짜에 몰아넣지 않는다. |
| PLAN-15 | 계획과 연결되지 않거나 수동 확인 총액과 섞여 실제일을 주 날짜로 표시할 수 없는 통장 출금은 계획표에서 별도의 읽기 전용 실제 행으로 보존한다. 달력과 같은 원본 거래 식별·중복·계좌 검증을 사용하며 이미 실제로 표현된 거래를 다시 표시하지 않는다. 이 행은 계획·거래를 새로 저장하거나 확인 버튼을 제공하지 않으며 원예산·실적·남은 예정·필요자금·잔액 계산에 다시 합산하지 않는다. 내부 자금이동·대여금도 통장 출금 사실로 표시하되 비용으로 단정하지 않는다. |

월별·계속 적용, 제외 우선순위, 할부 종료와 저장 방식은 [월 고정비와 유한 할부 계획](CASH_PLAN_SERIES.md)을 따른다.

## 5. 설치별 분류·제외 범위

개별 분류 규칙은 해당 설치의 공동 DB에서 관리한다. 문서의 예시는 합성 정책이며 실제 자료를 일괄 수정하는 지시가 아니다. 사용자 지시의 사업자·계좌·입출금·기간·정확한 일치 조건을 확인하고 기존 수동 분류를 보존한다.

| ID | 대상과 범위 | 기준 |
| --- | --- | --- |
| CAT-01 | 설치자가 선택한 과거 미분류 기준일 | 기본은 비활성화다. `installation-policy.ts`의 `historicalCompletionBefore`와 저장된 `과거완료` 과목이 함께 있을 때만 적용한다. 이미 분류한 과목은 보존하고 이후 자동 학습 근거로 사용하지 않는다. |
| CAT-02 | 설치자가 승인한 소액 확인 입금 규칙 | 입금·출금과 수동·자동 분류 범위를 구분한다. 예시의 금액이나 과목을 모든 설치에 강제하지 않는다. |
| CAT-03 | 거래처·급여·수수료 등 사용자 지정 과목 | 표시명 유사성이나 부분 일치만으로 사람·용도·방향을 추측하지 않는다. 사업자·계좌·기간·방향 등 저장된 조건 안에서 적용한다. |
| CAT-04 | 시트 사업자 별칭과 업종 참고치 | 기본 연결은 없다. 설치자가 정확한 표시명으로 명시하고 불명확하거나 복수 후보이면 연결하지 않는다. |
| EXC-01 | 저장된 월별·계속 제외 계획 | 새 달 생성·고정비 편집·동기화로 복원하지 않는다. 복원은 명시적으로 선택한 범위에서만 수행한다. |
| EXC-02 | 종료된 급여·할부·기타 반복 계획 | 종료 범위 이후에 재생성하지 않는다. 종료와 실제 납부 완료는 구분한다. |
| EXC-03 | 사업자간 받을·보낼 방향 | 가상 사업자 A가 B에게 받을 금액을 B가 받을 금액으로 뒤집지 않는다. 실제 이동과 원본 근거를 우선한다. |

`lib/finance/installation-policy.ts`의 업종 비교·추정 제외·시트 별칭은 빈 배열, 과거완료 기준일은 `null`이다. 이 파일은 클라이언트 번들에 포함되므로 공개 가능한 비민감 표시명만 설정하고 변경 후 다시 빌드한다. 개인별 정책·계좌번호·금융자료·비밀키를 넣지 않는다.

| DEV-07 | DB 변경은 마이그레이션과 적용·검증 기록을 남긴다. 기존 SQL Editor 적용과 CLI 이력을 확인하고 이미 적용한 SQL을 전체 push로 재실행하지 않는다. 인증·RLS·버전 충돌 검사를 우회하지 않는다. |
| DEV-08 | 기능 변경은 관련 테스트·연결 진단·빌드를 검증하고 커밋·푸시한다. DB가 바뀌면 대상 프로젝트에 먼저 적용·검증한다. Git 연동으로 자동 배포된 같은 커밋을 별도로 재배포하지 않는다. |
| DEV-09 | 커밋, GitHub push, DB 적용, Vercel Ready, 운영 화면 확인은 서로 다른 상태다. 정확한 커밋의 운영 배포와 실제 사용자 흐름을 확인한 뒤 완료로 보고한다. 단순 문서 저장은 GitHub 반영을 확인하고 앱 기능 배포 완료로 과장하지 않는다. |
| DEV-10 | 완료 보고에는 무엇을 바꿨고 어떻게 검증했으며 남은 제약이 무엇인지 짧게 적는다. 실행하지 않은 동기화·실제 납부·이체·권한 부여를 완료했다고 말하지 않는다. |

## 변경할 때 확인할 항목

1. 이번 요청에 관련된 규칙 ID와 사업자·계좌·기간·방향을 확인한다.
2. 기존 수동 분류·메모·계획 수정·계속 제외·원본 식별자가 유지되는지 확인한다.
3. 수집 → 저장 → 공동 자료 조회 → 계획·잔액 계산 → 각 화면까지 연결해 검증한다.
4. 요청으로 기준이 바뀌면 해당 ID의 문구·예외·관련 가이드와 테스트를 함께 갱신한다.
5. 실제 금융 증거와 인증정보는 저장소 밖의 접근 가능한 비공개 위치에 보관하고, 저장소에는 재현 가능한 합성 검증과 결과만 남긴다.

## 새 개발 환경에서 시작하기

1. 공개 저장소를 clone하고 [AGENTS.md](../AGENTS.md), [README](../README.md), 이 문서, [설치·개발 가이드](DEVELOPMENT.md)를 읽는다.
2. 현재 브랜치·미커밋 변경·다른 작업자의 담당 파일·잠금 파일과 미적용 DB 마이그레이션을 확인한다.
3. Node.js 22와 자신의 로컬 환경값을 준비하고 `npm ci`, `npm run doctor`, `npm test`, `npm run build`를 실행한다.
4. 새 설치는 자신의 Google 계정으로 로그인한 뒤 신뢰된 DB bootstrap으로 최초 관리자를 지정한다. 소유권·관리자 권한을 추측하지 않는다.
5. 요청 범위와 저장된 설정을 대조하고 기존 거래·수동 분류·메모·계획 수정·계속 제외를 보존한다.
