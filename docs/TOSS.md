# 토스페이먼츠 정산 예정 입금

사업자별 토스 정산 지급일과 순지급액을 가용자금 계획·달력에서 조회합니다. **토스 정산 동기화**는 기존 은행 거래나 계정과목을 수정하지 않으며, 결제 승인·취소·수동 정산 요청 API를 호출하지 않습니다.

## 서버 연결

1. 상점관리자와 개발자센터에서 **같은 상점아이디(MID)**의 라이브 시크릿 키를 확인합니다. 기존 키를 재발급하거나 기존 결제 연동을 교체할 필요가 없습니다.
2. 그 상점의 사업자와 실제 정산 입금 통장을 확인하고 기존 `fd_businesses.id`와 `fd_accounts.id`에 명시적으로 연결합니다. 상점명만으로 추측하거나 다른 사업자의 통장으로 연결하지 않습니다.
3. 자신의 호스팅 프로젝트에 서버 전용 `TOSS_SECRET_KEY`와 `TOSS_SETTLEMENT_MERCHANTS`를 설정합니다. 여러 MID는 서로 다른 `secretKeyEnv` 이름으로 같은 형식에 추가합니다.

```json
[
  {
    "merchantId": "YOUR_MID",
    "businessId": "EXISTING_BUSINESS_UUID",
    "accountId": "EXISTING_RECEIVING_ACCOUNT_UUID",
    "label": "상점 이름",
    "secretKeyEnv": "TOSS_SECRET_KEY"
  }
]
```

키는 `NEXT_PUBLIC_` 값·브라우저·저장소·로그·정산 테이블에 넣지 않습니다. 기존 `CLOBE_IMPORT_SIGNING_KEY`와 DB의 private verifier를 재사용하되, `toss-settlements-claim/save/release` 목적을 각각 분리해 서명합니다. 서버 환경변수를 바꾸면 새 배포에서 적용됩니다.

`TOSS_SYNC_ORIGIN`에는 자신의 앱 origin(예: `https://finance.example.com`)을 설정합니다. 미설정 시 유효한 Clobe 콜백 origin을 사용하며, 둘 다 없으면 연동을 구성하지 않습니다. 로컬 검증은 로컬 전용 origin과 격리된 DB를 사용합니다.

## 조회·저장

- `GET /api/toss/settlements`: 현재 서버에 연결된 MID의 안전한 저장 자료와 마지막 성공 동기화 범위를 반환합니다. 해제한 MID나 잘못된 사업자·통장 매핑의 자료는 현금 계산에서 제외합니다.
- `POST /api/toss/settlements`: 관리자 로그인과 정확한 Origin을 확인하고 빈 본문(`{}`)만 받습니다. 브라우저가 키·금액·사업자·통장·기간을 제출할 수 없습니다.
- 토스 공식 `GET https://api.tosspayments.com/v1/settlements`에 `dateType=paidOutDate`로 **지난달 1일~한국시간 오늘+90일**을 조회합니다. 모든 페이지와 모든 연결 MID가 정상 완료되어야 저장합니다. 한 페이지 최대 5,000건·한 실행 최대 20,000건이며 전체 요청은 240초로 제한합니다.
- 정산 지급액은 토스 `payOutAmount`의 부호를 그대로 보존합니다. 취소 금액을 추가로 빼거나 결제총액으로 예상 입금을 계산하지 않습니다. 취소 DTO가 양수 지급액 등 확인하지 못한 형식이면 안전하게 실패하고 기존 자료를 유지합니다.
- private 정산 테이블의 고유키는 공동 소유자+MID+`transactionKey`입니다. 같은 원본을 다시 조회해도 중복 추가하지 않습니다. 완료된 조회 범위의 원본 수정·삭제는 해당 정산 자료에만 반영합니다.
- 저장은 관리자·공동 소유자·서버 서명·기존 사업자와 통장을 검증하는 DB RPC 한 트랜잭션입니다. 실행 중 잠금과 짧은 재시도 제한이 있어 동시 실행이 오래된 자료를 덮어쓰지 않습니다. 실패 시 마지막 성공 시각과 자료를 유지합니다.

정산 기록은 결제 다음 날부터 API에 나타납니다. 아직 발생하지 않은 매출, 당일 새 결제, 타 PG의 정산, 지급 보류·수동 조정 등은 화면 합계와 차이가 있을 수 있어 최초 연결 시 실제 토스 화면과 대조해야 합니다. API 반환 지급일을 사용하며 임의의 4영업일 규칙으로 확정일을 만들지 않습니다.

## 중복 계산 방지

같은 사업자·같은 입금 통장·같은 정산 지급일의 여러 MID를 합산합니다. 저장된 은행 입금 중 토스페이먼츠임이 명시된 거래만 대조하고, 거래 ID 하나를 두 번 사용하지 않습니다. 같은 날짜·금액의 타사 입금이나 사업자간 자금이동은 매칭하지 않습니다.

| 표시 | 기준 | 가용자금에 더하는 금액 |
|---|---|---|
| 입금 예정 | 오늘 이후 지급일이며 합계가 양수 | 순정산액 |
| 입금 완료 | 같은 통장·지급일의 토스 입금 합계와 일치 | 0원 — 현재 통장 잔액과 중복 방지 |
| 확인 필요 | 당일 미확인, 입금 일부·차액, 원본 충돌, 순차감액 | 0원 |
| 입금 확인 필요/지급일 경과 | 과거 지급일인데 일치 입금이 없음 | 0원 |

위 표의 현금 가산 조건과 달력 표시는 별개입니다. 달력 전용 `tossCalendarIncome`은 선택 기간의 미래·오늘·과거 정산을 유지합니다. 미래에는 ‘입금 예정’, 오늘 미확인은 ‘오늘 입금 확인 필요’, 지난 미확인은 ‘지급일 경과 · 입금 확인 필요’, 통장 일치 후에는 ‘입금 완료’로 같은 지급일에 표시합니다. 지출 없는 날과 입금만 있는 사업자도 표시합니다. 부분 입금·차액·원본 충돌은 원정산액과 확인된 통장 금액을 구분하며 차액을 확정 받을 금액으로 가산하지 않습니다. 승인·취소 합산 0원과 순차감액도 일반 입금 완료·양수 예정과 구분합니다.

표시 전용 DTO의 `noCash:true`는 금융 계산의 입력으로 사용하지 않는다는 계약입니다. 현금·부족액·미래 정산 투영은 기존 `tossFundingIncome`의 미래 양수 미확인 정산만 사용합니다. 오늘로 날짜가 바뀌어 상태가 변경되더라도 달력에서 사라지지 않으며, 이미 입금된 정산이 잔액에 두 번 더해지지 않습니다.

현재 기록 잔액은 은행 잔액 그대로 유지합니다. 정산 예정액은 별도 예상 수입이며 계정과목 매출 실적에 다시 더하지 않습니다. 필요한 계정과목은 기존 거래 분류 경로를 사용합니다. Clobe 통장 동기화로 거래와 잔액이 바뀌면 동일 저장 정산을 다시 대조합니다. 당일 입금 여부를 증명할 수 없다면 현재 잔액에 이미 포함됐을 가능성을 막기 위해 예정액으로 자동 가산하지 않습니다.

## DB 적용·검증

마이그레이션: `supabase/migrations/20261102003146_toss_settlements.sql`.

자신의 Supabase 프로젝트에 전체 마이그레이션을 순서대로 적용합니다. 기존 설치는 적용 이력을 확인하고 미적용 파일만 실행합니다. 세 private 테이블 모두 RLS를 켜고 브라우저 역할의 직접 읽기·쓰기를 차단합니다. public RPC는 INVOKER 래퍼이고 private 코어에서 관리자·소유자와 서명을 검증합니다. 익명 RPC 실행은 차단합니다.

검증은 합성 API·입금·정산 자료와 로컬 PGlite를 사용합니다. 분할 페이지·동일 ID 재조회·취소 부호·원본 충돌·일부 조회 실패·관리자 격리·다른 통장 거부·재시도·범위 갱신·은행 원장과 편집 계획 불변을 확인합니다. 각 설치의 DB 적용과 실제 연동 화면 확인은 배포 담당자가 별도로 기록합니다.

공식 문서: [정산 API](https://docs.tosspayments.com/reference#정산-조회), [API 키](https://docs.tosspayments.com/reference/using-api/api-keys), [인증과 키 보관](https://docs.tosspayments.com/reference/using-api/authorization).
